## 一、调度系统 ⭐⭐⭐

### 1.1 主流调度系统对比

| 系统 | 语言 | 调度模型 | 特点 | 适用 |
| --- | --- | --- | --- | --- |
| **Crontab + Shell** | Shell | 单机定时 | 极简，无依赖、无重试、无可视化 | 小任务 |
| **Azkaban** | Java | 有向无环 | 轻量、配置文件驱动、Web UI | 中小规模 |
| **Oozie** | Java | Workflow + Coordinator | Hadoop 原生，XML 配置繁琐 | 传统 CDH 集群 |
| **DolphinScheduler** ⭐ | Java | 可视化 DAG，Master/Worker 去中心化 | 国产、可视化拖拽、多租户、数据质量集成、支持 Spark/Flink/MR/Shell/Python/SQL | 国内主流 |
| **Airflow** ⭐ | Python | Python DAG 代码定义 | 生态最大、Operator 丰富、代码即工作流 | 国际化团队、需灵活编排 |
| **DataWorks / EMR Workflow** | — | 云托管 | 一体化（开发+调度+治理+质量） | 阿里云用户 |

### 1.2 Airflow 核心概念 ⭐⭐

- [ ] **DAG**：有向无环图，定义任务与依赖
- [ ] **Task**：单个节点，由 Operator 实例化
- [ ] **Operator**：任务类型（`BashOperator`、`PythonOperator`、`SparkSubmitOperator`、`HiveOperator`、`KubernetesPodOperator`）
- [ ] **Sensor**：等待条件的特殊 Operator（`ExternalTaskSensor`、`HivePartitionSensor`、`FileSensor`）
- [ ] **XCom**：Task 之间传递小量数据（不适合大数据量）
- [ ] **Executor**：`SequentialExecutor`（调试）/ `LocalExecutor` / `CeleryExecutor`（分布式）/ `KubernetesExecutor`（弹性）
- [ ] **调度周期概念**：`schedule_interval` + `execution_date`（**注意：execution_date 是区间开始时间，不是实际运行时间** —— 高频踩坑点）
- [ ] **Backfill**：`airflow dags backfill -s 2024-01-01 -e 2024-01-31`

```python
with DAG('dwd_order_daily', schedule='0 2 * * *', catchup=False,
         default_args={'owner':'data','retries':3,'retry_delay':timedelta(minutes=5)}) as dag:
    check = ExternalTaskSensor(task_id='wait_ods', external_dag_id='ods_order', external_task_id='sync')
    etl   = SparkSubmitOperator(task_id='etl', application='hdfs:///jars/dwd.jar', conf={'spark.executor.memory':'8g'})
    dq    = PythonOperator(task_id='quality_check', python_callable=check_row_count)
    check >> etl >> dq
```

### 1.3 DolphinScheduler 核心概念 ⭐⭐

- [ ] 架构：MasterServer（DAG 切分与调度）+ WorkerServer（任务执行）+ ApiServer + AlertServer + ZooKeeper（注册中心与容错）
- [ ] **去中心化设计**：Master/Worker 均无单点，通过 ZK 注册与容错
- [ ] 任务类型：Shell、SQL、Spark、Flink、MR、Python、Procedure、SubProcess、Dependent（跨工作流依赖）、DataQuality
- [ ] **依赖节点（Dependent）**：实现跨工作流、跨周期的依赖（如依赖昨天某任务成功）
- [ ] 多租户：租户对应 Linux 用户，实现权限与资源隔离
- [ ] 定时与补数：支持定时、依赖触发、手动补数（指定日期区间）

### 1.4 调度依赖设计 ⭐⭐⭐（高频）

- [ ] **依赖类型**：
  - 同周期依赖（今天的 A 依赖今天的 B）
  - 跨周期依赖（今天的 A 依赖昨天的 A —— 自依赖，用于拉链表、增量合并）
  - 跨工作流依赖
- [ ] **SLA 设计**：给每层设定产出时间承诺（ODS 02:00 → DWD 04:00 → DWS 06:00 → ADS 08:00），倒推每层预算
- [ ] **关键路径分析**：找出 DAG 中耗时最长的链路，优先优化
- [ ] **失败处理策略**：
  - 重试次数与间隔（指数退避）
  - 失败告警（企业微信/钉钉/邮件/电话）分级：P0 电话、P1 IM、P2 邮件
  - 阻塞下游 vs 跳过（要有「强制成功」审批机制）
- [ ] **基线管理**：核心链路设置基线时间，预测是否会破线并提前告警（DataWorks 的基线概念）

- [ ] 追问：任务失败重跑会不会导致数据错误？（要求任务**幂等**：分区级 `INSERT OVERWRITE`、参数化日期、避免 `INSERT INTO` 追加）
- [ ] 追问：调度系统自己挂了怎么办？（Master/Worker 多实例 + ZK 容错；元数据库高可用；作业状态持久化，重启后从断点续跑）
- [ ] 追问：几万个任务，调度系统怎么扛住？（分片调度、任务分组、依赖关系存图数据库/内存、异步派发、Worker 池化、削峰）

## 二、数据开发工程化 ⭐⭐

### 2.1 代码与配置管理

- [ ] SQL/脚本纳入 Git 管理，分支开发 + Code Review + MR 合并
- [ ] **配置与代码分离**：日期、环境、连接串用参数（`${bizdate}`）注入，禁止硬编码
- [ ] 环境隔离：dev / test / prod 三套，元数据库与存储路径分离
- [ ] 命名规范：`{层级}_{主题域}_{业务过程}_{粒度/刷新方式}`，如 `dwd_trade_order_detail_inc`
- [ ] 表注释、字段注释强制要求（可加入 CI 校验）
- [ ] CI：SQL 语法检查、血缘影响分析、成本预估、危险操作拦截（无分区条件的全表扫描、`drop table`）

### 2.2 任务性能与稳定性规范

- [ ] 每个任务设置超时时间与资源上限
- [ ] 禁止 `select *`，禁止无分区过滤的全表扫描
- [ ] 大表 Join 前先过滤，聚合前先裁剪
- [ ] 关键任务设置重跑保护（避免并发重跑同一分区）
- [ ] 长链路任务拆分，便于失败重跑与并行

### 2.3 监控告警体系

| 层次 | 监控项 |
| --- | --- |
| 基础设施 | CPU、内存、磁盘、网络、HDFS 容量与副本健康 |
| 计算引擎 | YARN 队列使用率、pending container、Spark/Flink 作业状态 |
| 调度 | 任务失败数、延迟数、SLA 破线、长耗时 TopN |
| 数据质量 | 规则校验结果、行数波动、空值率、主键重复 |
| 实时链路 | Kafka Lag、Flink Checkpoint 成功率、端到端延迟、反压 |
| 数据服务 | 接口 QPS、RT、错误率 |

- [ ] 告警收敛：同源告警合并、抑制风暴、分级分人、值班轮转

## 三、数据资产与成本治理 ⭐⭐

### 3.1 资产盘点

- [ ] 表清单：负责人、业务域、层级、更新频率、存储量、生命周期、下游依赖数、最近访问时间
- [ ] 无用资产识别规则：
  1. N 天（如 90 天）无查询（依据 Hive Hook / Ranger Audit / 引擎访问日志）
  2. 无下游血缘依赖
  3. 责任人已离职且无人接手
- [ ] 下线流程：识别 → 通知责任人 → 冻结（停止更新）→ 观察期 → 归档（冷存储）→ 删除 → 记录

### 3.2 存储成本优化

- [ ] 冷热分层：HDFS 存储策略（HOT/WARM/COLD/ARCHIVE），历史分区自动降冷
- [ ] 生命周期（TTL）：ODS 明细保留 N 天，中间表保留更短
- [ ] 格式升级：TextFile → ORC/Parquet + Zstd，压缩率提升 30-70%
- [ ] 小文件合并：定期 compaction（湖格式自带）
- [ ] 分区裁剪：避免过度分区（如按小时分区但只按天查）
- [ ] 副本策略：非核心数据降副本数（3 → 2）+ 依赖 EC 纠删码（存储降到 1.5x）

### 3.3 计算成本优化

- [ ] 任务时长 TopN 优化（数据倾斜、资源不足、SQL 写法）
- [ ] 重复计算合并：多个下游读同一份中间结果，抽公共层
- [ ] 资源队列配额与优先级：核心链路高优，探索性任务低优 + 抢占
- [ ] 错峰调度：把非核心任务从凌晨高峰挪走
- [ ] Spot/抢占式实例跑非核心任务（云上）
- [ ] 量化话术：「通过 X 项治理，日均计算资源下降 Y%，月成本节省 Z 万」

## 四、数据服务层 ⭐

- [ ] 常见形态：
  - **JDBC 直连 OLAP**（Doris/StarRocks/CK）—— BI 报表
  - **数据 API 服务**（统一网关 + 限流 + 鉴权 + 缓存）—— 业务系统调用
  - **推送到业务库**（MySQL/HBase/Redis）—— 低延迟点查
- [ ] 工具：DataAPI、Kyuubi（Spark SQL 网关）、Trino、自研 Spring Boot 服务
- [ ] Kyuubi ⭐：多租户 Spark SQL 网关，共享 Engine 降成本，兼容 Hive JDBC，支持资源隔离
- [ ] 设计要点：接口幂等、超时熔断、结果缓存、慢查询治理、权限与脱敏
