# 10 · 分布式理论与中间件

> 对应排期：W7 D5-D7
> 定位：⭐⭐。用于应对交叉面和 Leader 面的基础考察，也是回答架构设计题的理论支撑。

## 一、分布式理论 ⭐⭐⭐

### 1.1 CAP

- [ ] **C（一致性）**：所有节点在同一时刻看到相同数据
- [ ] **A（可用性）**：每个请求都能在合理时间内得到非错误响应
- [ ] **P（分区容错性）**：网络分区发生时系统仍能工作 —— **分布式系统中 P 必选**
- [ ] 因此实际是 **CP vs AP 的取舍**：
  - CP：ZooKeeper、HBase、Etcd、Redis（默认）—— 分区时拒绝服务保证一致
  - AP：Eureka、Cassandra、DynamoDB、Kafka（部分场景）—— 分区时仍可用但可能读到旧数据
- [ ] 追问：Kafka 是 CP 还是 AP？（可配置：`acks=all` + `min.insync.replicas=2` + `unclean.leader.election=false` 偏 CP；`acks=1` + 允许 unclean 选举偏 AP）
- [ ] 追问：Nacos 呢？（同时支持 CP（Raft，用于配置）和 AP（Distro，用于服务发现），可切换）

### 1.2 BASE

- [ ] Basically Available（基本可用）、Soft state（软状态）、Eventually consistent（最终一致）
- [ ] 是 AP 的工程化落地，是对强一致的妥协 —— 大数据链路（实时数仓、CDC 同步）大多是最终一致

### 1.3 一致性协议 ⭐⭐

| 协议 | 代表 | 核心 |
| --- | --- | --- |
| **Paxos** | Chubby | 理论完备但难实现（Basic/Multi Paxos） |
| **Raft** ⭐ | Etcd、Consul、Nacos、Kafka KRaft | Leader 选举 + 日志复制 + 安全性，易理解 |
| **ZAB** | ZooKeeper | 崩溃恢复 + 消息广播，类 Paxos |

**Raft 关键点**（能讲清即可）：
1. **Leader 选举**：Term 任期 + 随机超时 + 多数派投票；只有日志最新的候选者能当选
2. **日志复制**：Client → Leader → 并行发 AppendEntries → 过半确认后 commit → 应用状态机
3. **安全性**：已提交的日志不会丢失/被覆盖
- [ ] 追问：为什么需要多数派（quorum）？（保证任意两个多数派集合必有交集，避免脑裂产生两个已提交的不同日志）
- [ ] 追问：脑裂怎么防？（过半机制 + Fencing/隔离旧 Leader + Lease 租约）

### 1.4 分布式事务 ⭐⭐

| 方案 | 一致性 | 性能 | 说明 |
| --- | --- | --- | --- |
| **2PC（两阶段提交）** | 强 | 低（同步阻塞、单点） | 准备阶段 + 提交阶段；Flink Sink、XA 用它 |
| **3PC** | 强 | 中 | 增加 CanCommit + 超时机制，缓解阻塞，仍难实现 |
| **TCC** | 最终 | 高 | Try-Confirm-Cancel，业务侵入强，需处理空回滚/悬挂/幂等 |
| **本地消息表** | 最终 | 高 | 业务与消息同库事务，定时补偿投递 |
| **事务消息**（RocketMQ） | 最终 | 高 | Half Message + 本地事务 + 回查 |
| **Saga** | 最终 | 高 | 长事务，每步有补偿动作 |
| **最大努力通知** | 弱 | 高 | 重试 + 主动查询对账 |

- [ ] 追问：Flink 的 Exactly-Once Sink 属于哪种？（2PC：`preCommit` 随 Checkpoint 快照，`commit` 在 Checkpoint 完成后执行）
- [ ] 追问：2PC 的问题？（同步阻塞、协调者单点、数据不一致风险（第二阶段部分节点未收到 commit））
- [ ] 追问：幂等怎么实现？（唯一索引/主键、去重表 + 唯一键、Token 机制、状态机、版本号 CAS）

### 1.5 分布式 ID ⭐

| 方案 | 特点 |
| --- | --- |
| UUID | 无序（导致 B+ 树页分裂）、占空间 |
| 数据库自增/号段模式 | 简单；号段（一次取一批）减少 DB 压力 —— 美团 Leaf-segment |
| Redis INCR | 快，需保证持久化与高可用 |
| **Snowflake** ⭐ | 64 位：1 符号 + 41 时间戳 + 10 机器 ID + 12 序列号；本地生成、趋势递增；**时钟回拨问题** |
| Leaf-Snowflake | 用 ZK 管理 workerID + 时钟校验，解决时钟回拨 |

- [ ] 追问：Snowflake 时钟回拨怎么处理？（拒绝生成并等待 / 记录上次时间戳，回拨小于阈值则等待，大于阈值则报警或用备用位 / 使用 Leaf 的 ZK 持久化时间戳校验）

## 二、MySQL ⭐⭐⭐

### 2.1 索引 ⭐⭐⭐（必考）

**B+ 树为什么适合做索引**：
1. 非叶子节点只存 key，单页能存更多索引项 → 树更矮（3-4 层可支撑千万级）→ 磁盘 IO 次数少
2. 叶子节点用双向链表连接 → 范围查询高效
3. 所有数据都在叶子 → 查询性能稳定

**聚簇索引 vs 二级索引**：
- InnoDB 主键索引 = 聚簇索引，叶子节点存**整行数据**
- 二级索引叶子存**主键值** → 查询非索引列需**回表**
- **覆盖索引**：查询列都在索引中，无需回表（`explain` 中 `Extra: Using index`）

**索引失效场景** ⭐⭐⭐：
1. 对索引列使用函数或运算：`where date(create_time)='2024-01-01'`
2. 隐式类型转换：`where phone = 13800138000`（phone 是 varchar）
3. 前导模糊：`like '%abc'`（`'abc%'` 可用）
4. 违反**最左前缀**原则：联合索引 `(a,b,c)`，只查 b、c
5. OR 两侧有一侧无索引
6. `!=`、`not in`、`is not null`（视数据分布，可能失效）
7. 优化器判断全表扫更快（返回行数占比过大）

**其他要点**：
- [ ] 联合索引最左前缀 + 索引下推（ICP，MySQL 5.6+，`Using index condition`）
- [ ] 自增主键 vs UUID：自增顺序插入，页分裂少；UUID 随机插入导致页分裂与碎片
- [ ] `explain` 关键字段：`type`（system > const > eq_ref > ref > range > index > ALL）、`key`、`rows`、`Extra`（Using filesort / Using temporary 是危险信号）

### 2.2 事务与隔离级别 ⭐⭐⭐

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| --- | :-: | :-: | :-: |
| Read Uncommitted | ✓ | ✓ | ✓ |
| **Read Committed（RC）** | ✗ | ✓ | ✓ |
| **Repeatable Read（RR，MySQL 默认）** | ✗ | ✗ | 基本解决（MVCC + 间隙锁） |
| Serializable | ✗ | ✗ | ✗ |

**MVCC**：
- 隐藏列 `DB_TRX_ID`（最后修改事务 ID）、`DB_ROLL_PTR`（指向 undo log 版本链）
- **ReadView**：`m_ids`（活跃事务列表）、`min_trx_id`、`max_trx_id`、`creator_trx_id`
- RC：每次查询生成新 ReadView；RR：事务首次查询生成后复用 → 这就是「可重复读」的原因
- 当前读（`select ... for update`、update、delete）走锁，读最新数据

**锁**：
- [ ] 行锁（Record Lock）、间隙锁（Gap Lock）、临键锁（Next-Key Lock = 行锁 + 间隙锁，用于 RR 下防幻读）
- [ ] 共享锁 S / 排他锁 X；意向锁 IS/IX（表级，加速锁判断）
- [ ] 死锁：InnoDB 自动检测并回滚代价小的事务（`innodb_deadlock_detect`）；预防：固定加锁顺序、缩小事务、降低隔离级别

### 2.3 日志 ⭐⭐⭐

| 日志 | 层级 | 作用 |
| --- | --- | --- |
| **redo log** | InnoDB 引擎层 | 崩溃恢复，保证**持久性**（WAL：先写日志再写数据页），循环写 |
| **undo log** | InnoDB 引擎层 | 事务回滚（**原子性**）+ MVCC 版本链 |
| **binlog** | Server 层 | 主从复制、数据恢复、**CDC 采集源**，追加写，三种格式（Statement/Row/Mixed） |

**两阶段提交（redo log 与 binlog 一致性）** ⭐⭐⭐：
```
1. redo log 写入，状态 = prepare
2. binlog 写入并 fsync
3. redo log 状态 = commit
崩溃恢复时：redo prepare 且 binlog 完整 → 提交；否则回滚
```
- [ ] 追问：为什么需要两阶段提交？（保证 redo log 与 binlog 一致，否则主从数据会不一致）
- [ ] 追问：CDC 用 binlog 的哪种格式？（**Row 格式**，记录每行变更前后镜像，才能解析出具体字段变化）

### 2.4 主从复制与分库分表 ⭐⭐

**主从复制流程**：
```
Master: 事务 → binlog → dump 线程推送
Slave:  IO 线程接收 → relay log → SQL 线程回放
```
- [ ] 复制模式：异步（默认，可能丢）、半同步（至少一个从库 ack）、组复制 MGR（多数派）
- [ ] 主从延迟原因：大事务、单线程回放（5.7+ 支持并行复制）、从库负载高、网络
- [ ] 追问：如何解决读写分离下的主从延迟读到旧数据？（强制走主库、半同步、延迟监控 + 路由降级、业务容忍）

**分库分表**：
- [ ] 垂直拆分（按业务/字段拆）vs 水平拆分（按行拆）
- [ ] 分片键选择：查询高频字段、分布均匀（用户 ID hash、订单 ID 基因法）
- [ ] 分片算法：取模（均匀，扩容需迁移）、范围（易热点，扩容简单）、一致性哈希（扩容迁移量小）
- [ ] 带来的问题：跨库 Join、分布式事务、全局唯一 ID、跨分片分页排序、扩容迁移
- [ ] 工具：ShardingSphere（Sharding-JDBC / Proxy）、MyCat
- [ ] 追问：数据量到亿级，除了分库分表还有什么选择？（归档冷数据、读写分离 + 从库扩容、换存储引擎（HBase/TiDB/Doris）、业务上避免全量扫描）

## 三、Redis ⭐⭐

### 3.1 数据结构与场景

| 类型 | 底层实现 | 大数据场景 |
| --- | --- | --- |
| String | SDS | 计数器、缓存、分布式锁 |
| Hash | ziplist / hashtable | 维度对象缓存 |
| List | quicklist | 消息队列、最新 N 条 |
| Set | intset / hashtable | 去重、共同好友、UV |
| ZSet | ziplist / **skiplist + hashtable** | 排行榜、TopN、延迟队列 |
| Bitmap | String 位操作 | 签到、活跃用户标记（超省空间） |
| HyperLogLog | — | **基数统计（UV），12KB 存亿级，误差 0.81%** |
| Geo | ZSet | 地理位置 |
| Stream | radix tree | 消息队列（支持消费组） |

- [ ] 追问：跳表为什么不用红黑树？（实现简单、范围查询天然有序、并发友好、内存局部性可调）
- [ ] 大数据高频：Flink 结果写 Redis 做实时大屏缓存；维表放 Redis 做 Lookup；Bitmap 做日活

### 3.2 持久化 ⭐⭐⭐

| 方式 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **RDB** | 定时全量快照（fork 子进程 + COW） | 文件紧凑、恢复快 | 可能丢最后一次快照后的数据 |
| **AOF** | 追加写命令日志 | 数据更安全（everysec 最多丢 1s） | 文件大、恢复慢 |
| **混合持久化**（4.0+） | AOF 重写时前半段 RDB 格式 + 后半段增量命令 | 兼顾恢复速度与安全 | 推荐 |

- [ ] AOF 刷盘策略：`always`（每命令，慢）、`everysec`（默认，折中）、`no`（OS 决定）
- [ ] AOF 重写：`auto-aof-rewrite-percentage=100`、`auto-aof-rewrite-min-size=64mb`

### 3.3 高可用

- [ ] **主从复制**：全量同步（RDB + 缓冲区）+ 增量同步（repl backlog，断线重连靠 offset）
- [ ] **哨兵 Sentinel**：监控 + 自动故障转移（主观下线 → 客观下线 → 选举哨兵 Leader → 选新主 → 通知）
- [ ] **Cluster 集群**：16384 个 slot，CRC16(key) % 16384 定位；分片 + 自动故障转移；不支持多 key 跨 slot 操作（可用 hash tag `{}`）

### 3.4 经典问题 ⭐⭐⭐

| 问题 | 定义 | 解决 |
| --- | --- | --- |
| **缓存穿透** | 查询根本不存在的数据，绕过缓存直打 DB | ① 缓存空值（短 TTL）② **布隆过滤器** ③ 参数校验 ④ 接口限流 |
| **缓存击穿** | 某个热点 key 过期瞬间，大量请求打 DB | ① **互斥锁/单飞**（只让一个请求回源）② 热点 key 逻辑过期不物理过期 ③ 永不过期 + 异步更新 |
| **缓存雪崩** | 大量 key 同时过期或 Redis 宕机 | ① 过期时间加随机抖动 ② Redis 高可用集群 ③ 多级缓存（本地 + Redis）④ 熔断降级限流 |
| **缓存与 DB 一致性** | 双写不一致 | **Cache Aside**：先更新 DB，再删除缓存（不是更新）；配合 binlog 订阅（Canal）异步删缓存；延迟双删 |
| **大 key** | 单 key 过大（>10KB / 集合元素过多） | 拆分、压缩、`unlink` 异步删除、监控 `redis-cli --bigkeys` |
| **热 key** | 单 key QPS 极高 | 本地缓存（Caffeine）、多副本打散（key 加后缀随机读）、读写分离 |

- [ ] 追问：为什么是「删除缓存」而不是「更新缓存」？（并发写会导致旧值覆盖新值；删除是幂等的、懒加载更省资源）
- [ ] 追问：先删缓存还是先更新 DB？（先删缓存 + 后更新 DB 会有并发读把旧值重新写回缓存的问题 → 用延迟双删；主流推荐**先更新 DB 再删缓存**，配合 binlog 兜底）

### 3.5 分布式锁 ⭐⭐

```bash
SET lock_key unique_value NX PX 30000        # 原子加锁
# 释放：Lua 脚本保证「判断是自己的锁 + 删除」原子性
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else return 0 end
```
- [ ] 要点：唯一 value（防误删）、超时时间（防死锁）、Lua 原子释放、**看门狗续期**（Redisson 默认 30s，每 10s 续期）
- [ ] RedLock：多个独立 Redis 节点，多数派加锁成功才算成功（有争议，Martin Kleppmann 质疑其在时钟漂移/GC 停顿下的安全性）
- [ ] 更可靠的方案：ZooKeeper 临时顺序节点（天然解决续期与脑裂）

### 3.6 性能

- [ ] 单线程为什么快？（纯内存 + 单线程避免锁竞争与上下文切换 + IO 多路复用 epoll + 高效数据结构）
- [ ] Redis 6.0 引入多线程：仅用于**网络 IO 读写与协议解析**，命令执行仍单线程
- [ ] Pipeline 批量、Lua 脚本、避免 `keys *`（用 `scan`）

## 四、HBase ⭐

- [ ] 数据模型：RowKey + Column Family + Qualifier + Timestamp → 多版本
- [ ] 架构：HMaster（元数据、Region 分配）+ RegionServer（Region 服务）+ ZooKeeper
- [ ] **写流程**：Client → WAL(HLog) → MemStore（内存）→ 达阈值 flush 到 HFile → 后台 Compaction 合并
- [ ] **读流程**：MemStore + BlockCache + 多个 HFile 合并读（Bloom Filter 加速）
- [ ] **LSM-Tree**：写优化的核心（顺序写 WAL + 内存排序 + 后台合并），也是 RocksDB / Paimon 的基础
- [ ] RowKey 设计三原则 ⭐⭐：
  1. **唯一性**：RowKey 是唯一标识
  2. **散列性**：避免热点 → 加盐前缀 / 哈希前缀 / 反转（如手机号反转）
  3. **长度原则**：越短越好（建议 < 100 字节），因为每个 KV 都存 RowKey
- [ ] 适用场景：海量数据高并发点查/范围扫、时序数据、用户画像宽表、消息存储
- [ ] 不适用：复杂 Join、多条件查询（需配合二级索引/Phoenix/ES）

## 五、Elasticsearch ⭐

- [ ] 核心：倒排索引（Term → DocID 列表）、分片（Primary/Replica）、近实时（refresh 1s）
- [ ] 写入流程：Coordinate → Primary Shard（内存 buffer + translog）→ Replica → refresh 生成 segment → flush 落盘
- [ ] 大数据场景：日志检索、实时指标查询、维表模糊搜索、用户画像标签查询
- [ ] 与 HBase/OLAP 的分工：ES 擅长全文检索与多维过滤，不擅长精确聚合大数据量（用 Doris/CK）
