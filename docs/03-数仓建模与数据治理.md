# 03 · 数仓建模与数据治理

> 对应排期：W2
> 定位：⭐⭐⭐ 核心。3-5 年经验的面试二面几乎必深挖这一章，是区分「SQL Boy」和「数仓工程师」的关键。

## 一、数仓基础概念 ⭐⭐

- [ ] 数据仓库四大特征（Inmon）：**面向主题、集成、相对稳定、反映历史变化**
- [ ] OLTP vs OLAP：

| 维度 | OLTP | OLAP |
| --- | --- | --- |
| 场景 | 交易、增删改 | 分析、聚合查询 |
| 数据量 | GB 级 | TB-PB 级 |
| 表结构 | 高度范式化（3NF） | 反范式（星型/雪花） |
| 存储 | 行存 | 列存 |
| 并发 | 高并发短事务 | 低并发复杂查询 |
| 典型 | MySQL、Oracle | Hive、Doris、ClickHouse |

- [ ] 为什么要建数仓？（业务库分散、结构面向事务不适合分析、历史数据被清理、查询影响生产库、需要统一口径）

## 二、分层架构 ⭐⭐⭐（必考）

### 2.1 标准分层

```
┌─────────────────────────────────────────────────────┐
│  ADS / APP   应用数据层  ── 面向具体报表/接口的结果数据      │
├─────────────────────────────────────────────────────┤
│  DWS         汇总数据层  ── 按主题轻度汇总（宽表、指标）      │
├─────────────────────────────────────────────────────┤
│  DWD         明细数据层  ── 清洗后的原子事实明细，维度退化    │
│  DIM         维度层      ── 一致性维度表                    │
├─────────────────────────────────────────────────────┤
│  ODS         原始数据层  ── 贴源，保持原貌，仅做压缩/分区     │
└─────────────────────────────────────────────────────┘
              ↑
     数据源：业务库 / 日志 / 埋点 / 第三方
```

### 2.2 每层职责与设计要点

| 层 | 职责 | 关键设计点 | 存储策略 |
| --- | --- | --- | --- |
| **ODS** | 贴源存储，与源系统结构一致 | 外部表、不做业务清洗、保留原始字段、按天分区、增量/全量标记 | 长期保留（或压缩归档） |
| **DWD** | 数据清洗、脱敏、维度退化、构建原子事实 | 一行 = 一个业务过程事件；空值/脏数据处理；口径统一 | 长期保留 |
| **DIM** | 一致性维度 | SCD 处理（拉链表）、维度整合（多源合并）、代理键 | 全量快照或拉链 |
| **DWS** | 主题汇总、构建派生指标 | 按天/周/月 + 主题聚合；宽表化减少 Join | 中期保留 |
| **ADS** | 面向应用的最终结果 | 直接对接报表/接口，字段贴合业务口径 | 短期，可同步到 MySQL/Doris |

### 2.3 为什么要分层（⭐⭐⭐ 必答）

1. **解耦**：隔离源系统变化，源表结构调整只影响 ODS/DWD
2. **复用**：DWD/DWS 一份数据服务多个 ADS，避免重复计算和口径不一致
3. **可维护**：问题定位分层排查，血缘清晰
4. **性能**：预聚合减少下游扫描量
5. **成本**：中间结果复用，避免每次从 ODS 全量扫描

- [ ] 追问：分层会带来什么问题？（链路变长、延迟累积、存储成本上升、口径传递失真、排查跨多层）
- [ ] 追问：什么情况下可以减少层级？（小团队/轻量场景可 ODS→DWD→ADS；实时链路为了延迟常做 DWD 直出）
- [ ] 追问：怎么防止「烟囱式」重复建设？（统一指标管理平台、DWS 强制复用、需求评审 + 血缘审计、公共层 SLA 承诺）

### 2.4 增量与全量策略 ⭐⭐⭐

| 类型 | 适用 | 做法 |
| --- | --- | --- |
| **每日全量** | 小表（维度表、配置表，< 千万行） | 每天一个 `dt` 分区存全量快照 |
| **每日增量** | 大表且源表有更新时间/自增 ID | 每天只抽当天变更数据到 `dt` 分区 |
| **增量合并全量** | 大表需要全量视图 | 昨日全量 + 今日增量 → merge 成今日全量（拉链或覆盖） |
| **拉链表** | 大表需查历史状态且存储受限 | `start_date/end_date` 记录有效期 |
| **Binlog CDC** | 需要捕获物理删除 | Canal / Flink CDC 实时同步 |

**增量合并全量的标准 SQL**：

```sql
INSERT OVERWRITE TABLE dwd_user_info_full PARTITION (dt = '${today}')
SELECT * FROM (
    SELECT *, row_number() OVER (PARTITION BY id ORDER BY src DESC) rn
    FROM (
        SELECT *, 1 AS src FROM ods_user_info_inc   WHERE dt = '${today}'
        UNION ALL
        SELECT *, 0 AS src FROM dwd_user_info_full   WHERE dt = '${yesterday}'
    ) u
) t WHERE rn = 1;
```

- [ ] 追问：如何处理源端物理删除？（增量方式无法感知 → 需 CDC binlog，或定期全量兜底校准，或用逻辑删除标记）
- [ ] 追问：数据重跑怎么保证幂等？（`INSERT OVERWRITE` 分区级覆盖 + 分区参数化，天然幂等）

## 三、维度建模 ⭐⭐⭐

### 3.1 建模方法论对比

| 方法论 | 代表 | 核心 | 适用 |
| --- | --- | --- | --- |
| **Inmon（自顶向下）** | EDW + 数据集市 | 先建企业级 3NF 数仓，再派生集市 | 大型企业、数据标准化要求高 |
| **Kimball（自底向上）** | 维度建模 | 从业务过程出发建星型模型，靠**一致性维度**串联总线 | 互联网主流，敏捷交付 |
| Data Vault | — | Hub/Link/Satellite，强审计与灵活性 | 金融、复杂整合场景 |

> 国内互联网绝大多数采用 **Kimball 维度建模**，面试重点在此。

### 3.2 维度建模四步法 ⭐⭐⭐（必背）

1. **选择业务过程**（Business Process）：如下单、支付、退款、加购、登录
2. **声明粒度**（Grain）：一行代表什么，越细越好，如「一个订单中的一个商品项」
3. **确认维度**（Dimensions）：谁、何时、何地、何物 —— 用户、时间、地区、商品
4. **确认事实**（Facts）：可度量的数值 —— 数量、金额、时长

### 3.3 模型类型

| 模型 | 结构 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **星型模型** | 事实表 + 反范式维度表（不再拆分） | 查询 Join 少、性能好、易理解 | 维度冗余、存储大 |
| **雪花模型** | 维度表进一步范式化拆分 | 存储省、维护规范 | Join 多、性能差 |
| **星座模型** | 多个事实表共享维度 | 企业级复用 | 复杂 |

- [ ] 生产选择：**优先星型模型**（数仓是空间换时间，OLAP 场景 Join 代价高）。雪花只在维度层级极深、存储敏感时使用。

### 3.4 事实表分类 ⭐⭐⭐

| 类型 | 说明 | 示例 |
| --- | --- | --- |
| **事务事实表** | 一行一个业务事件，不可修改，粒度最细 | 订单明细、点击日志、支付流水 |
| **周期快照事实表** | 固定周期对状态采样 | 每日账户余额、每日库存 |
| **累积快照事实表** | 记录流程各里程碑时间，会随流程推进被更新 | 订单从下单→支付→发货→签收的全周期 |

- [ ] 追问：累积快照怎么处理「更新」？（Hive 不支持 update → 每天重算整个未完结流程分区，或用拉链表/Hudi upsert）
- [ ] 事实表的度量类型：可加（金额、数量）、半可加（余额 —— 跨时间不可加）、不可加（比率、单价）

### 3.5 维度表设计 ⭐⭐⭐

**缓慢变化维 SCD（Slowly Changing Dimension）**：

| 类型 | 策略 | 说明 |
| --- | --- | --- |
| SCD Type 0 | 不变 | 保留原始值 |
| **SCD Type 1** | 直接覆盖 | 不保留历史，实现简单，最常用（如用户手机号） |
| **SCD Type 2** | 新增一行 | 加 `start_date/end_date/is_current`，保留全历史 → **拉链表** |
| SCD Type 3 | 新增列 | 保留前一个值（`old_city`, `new_city`） |
| SCD Type 4 | 历史表分离 | 当前表 + 历史表 |
| SCD Type 6 | 1+2+3 混合 | — |

- [ ] 追问：什么维度用 Type 1，什么用 Type 2？（不影响历史分析口径的用 Type 1，如联系方式；影响归因分析的用 Type 2，如用户等级、商品价格档位、地区归属）
- [ ] **退化维度（Degenerate Dimension）**：没有对应维度表的维度，直接放在事实表里，如订单号、运单号
- [ ] **杂项维度（Junk Dimension）**：把一堆低基数标记字段（是否首单、渠道类型、支付方式）组合成一张小维度表，减少事实表宽度
- [ ] **一致性维度（Conformed Dimension）**：跨业务过程统一口径的维度，是实现「总线架构」的基础
- [ ] 代理键 vs 自然键：代理键（自增/哈希）用于隔离源系统主键变化，Hive 中常用 `md5(concat(...))` 或 `monotonically_increasing_id`

## 四、指标体系 ⭐⭐⭐

### 4.1 指标分类（阿里 OneData 方法论）

| 概念 | 定义 | 示例 |
| --- | --- | --- |
| **原子指标** | 业务过程 + 度量，不可再拆 | 支付金额、订单数 |
| **修饰词** | 限定业务范围的词 | 近 7 天、无线端、新用户 |
| **时间周期** | 统计的时间窗口 | 1d / 7d / 30d / MTD |
| **派生指标** | 原子指标 + 时间周期 + 修饰词 | 近 7 天无线端新用户支付金额 |
| **衍生/复合指标** | 多个派生指标运算 | 客单价 = 支付金额 / 支付买家数 |

- [ ] 命名规范示例：`{时间周期}_{修饰词}_{原子指标}` → `1d_app_new_pay_amt`
- [ ] 追问：怎么解决「同名不同义、同义不同名」？（统一指标管理平台 + 指标字典 + 口径评审 + 血缘绑定，禁止业务方在报表层自行计算派生指标）

### 4.2 常见业务指标口径

- [ ] PV / UV / DAU / MAU / 新增 / 活跃 / 留存 / 流失
- [ ] GMV vs 实际支付金额（GMV 通常含未支付、已退款）
- [ ] 转化率漏斗：曝光 → 点击 → 详情页 → 加购 → 下单 → 支付
- [ ] 追问：DAU 怎么算才准？（去重口径：设备 ID vs 用户 ID；未登录用户如何处理；跨天活跃归属）
- [ ] 追问：留存的分母是什么？（新增留存分母=当日新增；活跃留存分母=当日活跃）

## 五、数据治理 ⭐⭐

### 5.1 数据质量

**六大维度**：完整性、准确性、一致性、及时性、唯一性、有效性

**质量校验规则设计**：

| 规则类型 | 示例 | 强度 |
| --- | --- | --- |
| 主键唯一性 | `count(1) = count(distinct id)` | 强（阻塞） |
| 非空校验 | 关键字段 null 率 < 0.1% | 强 |
| 值域校验 | 金额 >= 0，状态在枚举内 | 中 |
| 波动校验 | 今日行数较 7 日均值波动 < 30% | 中（告警） |
| 一致性校验 | DWS 汇总 = DWD 明细求和 | 强 |
| 及时性校验 | 产出时间 < SLA（如每日 08:00） | 强 |
| 引用完整性 | 事实表外键能在维度表找到 | 中 |

**落地方式**：
- [ ] 调度平台内置（DolphinScheduler 数据质量模块 / Airflow + Great Expectations）
- [ ] 独立平台：Apache Griffin、Deequ、Soda、dbt test
- [ ] 规则配置化：表 + 字段 + 规则类型 + 阈值 + 告警方式 + 是否阻塞下游
- [ ] 追问：强规则失败怎么办？（阻塞下游 + 告警值班 + 人工介入；要有「跳过」审批机制防止链路全挂）

### 5.2 元数据与血缘 ⭐⭐

- [ ] 元数据分类：技术元数据（表结构、存储位置、任务配置）、业务元数据（指标口径、责任人）、操作元数据（运行日志、访问记录）
- [ ] 工具：Apache Atlas、DataHub、OpenMetadata、Hive Metastore + 自建
- [ ] 血缘采集方式：
  1. SQL 解析（Antlr / Calcite 解析 insert-select，得到字段级血缘）—— 主流
  2. 引擎 Hook（Hive Hook、Spark Listener）—— 运行时采集，准确
  3. 调度平台任务依赖 —— 只能到表级
- [ ] 血缘的用途：影响分析（改字段影响哪些下游）、问题溯源（数据异常来自哪个上游）、成本分摊、下线无用表
- [ ] 追问：字段级血缘怎么实现？（解析 SQL AST → 遍历 select 表达式 → 建立 目标字段 ← 源字段 集合的映射，处理 `*`、子查询、UDF、CTE）

### 5.3 成本治理 ⭐（大厂高频）

- [ ] 存储治理：冷热分层（HDFS 存储策略 SSD/DISK/ARCHIVE）、生命周期 TTL、无用表下线、压缩格式升级、小文件合并
- [ ] 计算治理：任务运行时长 Top N 优化、重复计算合并、失败重试风暴治理、资源队列配额
- [ ] 无用资产识别：访问日志（Hive Hook / Ranger Audit）→ N 天无查询且无下游血缘 → 通知责任人 → 归档 → 删除
- [ ] 量化收益话术：「通过 XX 治理，存储下降 X%，任务平均时长下降 Y%，月均节省成本 Z 元」

### 5.4 数据安全与权限

- [ ] 认证：Kerberos / LDAP
- [ ] 授权：Apache Ranger（表/列/行级）、Hive 自带授权、Sentry（已淘汰）
- [ ] 脱敏：静态脱敏（落库时）vs 动态脱敏（查询时按角色 mask）
- [ ] 分级分类：公开 / 内部 / 敏感 / 机密；PII 字段识别与标记
- [ ] 审计：所有查询留痕，支持合规审查

## 六、数据同步与一致性 ⭐⭐

- [ ] 全量 vs 增量 vs 实时同步的取舍
- [ ] 双写问题：应用双写 DB + MQ 会不一致 → 用 CDC 单点采集
- [ ] 幂等设计：分区覆盖写、主键去重、版本号比较
- [ ] 数据回溯（Backfill）：参数化日期 + 分区覆盖 + 依赖顺序重跑
- [ ] 追问：如何保证离线和实时数据一致（口径一致）？
  - 指标口径统一定义，离线与实时共用同一套 SQL 语义（流批一体，如 Flink SQL + 数据湖）
  - Lambda 架构下用离线结果 T+1 修正实时结果
  - 建立对账任务：实时结果 vs 离线结果每日比对，差异超阈值告警

## 七、Lambda / Kappa / 流批一体 ⭐⭐⭐

| 架构 | 结构 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **Lambda** | 批处理层（准确）+ 速度层（实时）+ 服务层合并 | 兼顾准确与实时，容错好 | 两套代码两套口径，维护成本翻倍 |
| **Kappa** | 只保留流处理层，历史重跑靠重放消息队列 | 一套代码，逻辑统一 | 重放成本高（需保留长周期数据）、复杂 Join/聚合受限 |
| **流批一体** | 统一引擎（Flink/Spark）+ 统一存储（Iceberg/Hudi/Paimon）+ 统一 SQL | 真正一套代码，成本最低 | 生态成熟度、状态规模、批流语义差异仍有挑战 |

- [ ] 追问：你们用哪种？为什么？（准备好基于自身项目的回答，并说明演进路径）
- [ ] 追问：Kappa 怎么做历史数据回溯？（Kafka 长期保留 or 数据湖存原始流 → 新起 job 从最早 offset 重放 → 双跑对账 → 切流）

## 八、场景设计题演练 ⭐⭐⭐（Leader/二面必考）

> 每题练习方式：15 分钟内画出架构图 + 说清关键设计取舍。

1. **设计一个电商实时大屏**：GMV、订单量、TopN 商品，秒级更新。
   - 关键：埋点/binlog → Kafka → Flink（预聚合 + 去重）→ Redis/Doris → 大屏；
   - 考点：如何保证金额准确（幂等 + 状态去重）、TopN 怎么算（keyBy + 有序状态 or Doris 直接查）、大屏刷新压力
2. **从 0 搭建日增 10TB 的用户行为数仓**：
   - 关键：分层设计、采集方案、存储估算、调度依赖、SLA、质量监控
3. **设计一个用户画像标签体系**：
   - 关键：标签分类（统计类/规则类/模型类）、宽表 vs KV 存储、更新频率、标签血缘
4. **实时数仓如何保证 Exactly-Once**：
   - 关键：Source（Kafka offset 纳入 checkpoint）→ Flink（checkpoint + 两阶段提交）→ Sink（事务/幂等 upsert）
5. **业务方反馈某个指标数据不对，你怎么排查**：
   - 关键：口径确认 → 血缘定位链路 → 分层比对（ADS vs DWS vs DWD vs ODS vs 源库）→ 检查是否重跑/延迟/脏数据 → 修复 + 加质量规则防复发
6. **如何设计一套数据质量监控平台**：
   - 关键：规则配置化、调度集成、强弱规则、告警收敛、质量分报表、闭环处理
